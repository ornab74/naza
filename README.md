# Naza — SpookyNaza Secure LLM CLI & Experimental Risk Scanner

Naza is a local, encrypted LLM CLI and experimental decision-support scanner. The unified build combines the road and food/water scanning work with the **SpookyNaza** key-wrapping path and a pinned Open Quantum Safe backend.

This build consolidates the older overlapping Naza snapshots into one canonical repository. The virtual environment, generated bytecode, local build products, and duplicate source trees are intentionally excluded.

> **Important:** Naza is experimental decision-support software. A `Low`, `Medium`, or `High` result is not proof that a road, vehicle, food item, water source, device, or environment is safe or unsafe. Verify important decisions with direct observation, trusted measurements, appropriate testing, and professional or emergency guidance where relevant.

## What is enabled by default

The installer now treats the SpookyNaza cryptographic path as the standard installation, not an optional add-on.

Newly wrapped Naza keys default to:

```text
NAZA_CRYPTO_MODE=tri
NKEY4
ML-KEM-1024 + HQC-256 + X25519
HKDF-SHA512
AES-256-GCM
```

The implementation lives in `spooky_trihybrid.py` and `spooky_combiner.py`.

The installer also builds and verifies **Open Quantum Safe liboqs 0.14.0** automatically. Installation fails if the required `ML-KEM-1024` and `HQC-256` mechanisms are not available after the build.

## Pinned Open Quantum Safe backend

Naza ships:

```text
install_liboqs_0.14.0.sh
```

The normal installers run this script automatically. You do **not** need to install SpookyNaza/liboqs separately.

The native liboqs source archive is pinned to version `0.14.0` and checked before extraction:

```text
SHA-256:
5b0df6138763b3fc4e385d58dbb2ee7c7c508a64a413d76a917529e3a9a207ea
```

The `liboqs-python` wrapper is pinned to upstream commit:

```text
7906e7879a099fa34217035957d977314f99757d
```

with archive SHA-256:

```text
ed785fee58e43f20c042db97389ce63091b331278c24f63828c4b8dac0905f8c
```

Both archives are downloaded over HTTPS and SHA-256 verified before the corresponding untrusted archive contents are built or installed. The Python wrapper is installed directly into the active Naza virtual environment rather than with `pip --user`.

# Android installation — Termux + Ubuntu proot

This is the recommended Android layout. Android-backed keystore/fingerprint operations stay on the Termux side; Naza and liboqs run inside Ubuntu proot.

## Requirements

Install **Termux** and the matching **Termux:API companion app** from a compatible source. The shell package alone cannot provide the Android API service if the companion application is absent.

Then open Termux and run:

```bash
pkg update -y
pkg install -y git

git clone https://github.com/ornab74/naza.git
cd naza/termux-naza-autosetup
bash setup.sh
```

The setup script performs the rest automatically.

## What the Termux installer does

The installer:

1. updates Termux packages;
2. installs `proot-distro`, `termux-api`, Git, curl, and required host tools;
3. requires `termux-keystore` and `termux-fingerprint` to be available;
4. automatically creates the required Android keystore alias when missing;
5. verifies the alias before proceeding;
6. installs/reuses Ubuntu proot;
7. installs compiler, Python, OpenSSL and CMake dependencies inside Ubuntu;
8. clones Naza and creates its Python virtual environment;
9. installs Naza Python dependencies;
10. automatically builds the pinned liboqs 0.14.0 backend;
11. installs the pinned `liboqs-python` wrapper into the Naza venv;
12. verifies `ML-KEM-1024` and `HQC-256` are enabled;
13. verifies the SpookyNaza modules load;
14. configures `NAZA_CRYPTO_MODE=tri` for normal launches;
15. installs the Termux-side unlock and boot helpers.

## Required Termux keystore

The keystore is **not optional** in the Termux installation.

The installer automatically executes the equivalent of:

```bash
termux-keystore generate naza-unlock -a RSA -s 2048 -u 10
```

This happens in **Termux**, before Ubuntu proot setup continues.

The installer then verifies:

```bash
termux-keystore list
```

contains:

```text
naza-unlock
```

If the Android keystore command is unavailable, key generation fails, or the alias cannot be verified, installation stops instead of continuing without the unlock layer.

## Starting Naza on Android

After installation, reopen Termux or run:

```bash
naza
```

The launch flow requests the Termux-side fingerprint/keystore unlock first and then starts the Naza TUI inside Ubuntu proot with the pinned liboqs environment loaded and SpookyNaza tri-hybrid mode enabled.

Manual unlock and launch commands remain available:

```bash
naza-unlock
naza
```

# Native Ubuntu / Debian installation

Clone the repository and run the Ubuntu installer:

```bash
git clone https://github.com/ornab74/naza.git
cd naza
bash termux-naza-autosetup/setup_ubuntu.sh
```

Despite the directory name, `setup_ubuntu.sh` is the native Ubuntu/Debian installer and does not require Termux.

It installs the required build tools, creates `~/naza/venv`, installs Python dependencies, builds the pinned liboqs backend, installs the pinned Python wrapper into the venv, verifies the required KEMs, and keeps SpookyNaza tri-hybrid mode as the default.

Start Naza with:

```bash
~/naza/run_naza.sh
```

If you cloned to a custom `NAZA_APP_DIR`, run `run_naza.sh` from that directory instead.

# Manual pinned liboqs reinstall / verification

The normal setup scripts already install liboqs. This command is mainly for repairing or re-verifying an existing installation.

Activate Naza's virtual environment first:

```bash
cd ~/naza
source venv/bin/activate
export PYTHON_BIN="$PWD/venv/bin/python"
./install_liboqs_0.14.0.sh
```

Then launch through:

```bash
./run_naza.sh
```

`run_naza.sh` exports the expected `OQS_INSTALL_PATH`, updates `LD_LIBRARY_PATH`, and defaults `NAZA_CRYPTO_MODE` to `tri`.

# Usage

Start the unified TUI:

```bash
./run_naza.sh
```

or, from an already configured virtual environment:

```bash
export OQS_INSTALL_PATH="$HOME/.local/liboqs-0.14.0"
export LD_LIBRARY_PATH="$OQS_INSTALL_PATH/lib${LD_LIBRARY_PATH:+:$LD_LIBRARY_PATH}"
export NAZA_CRYPTO_MODE=tri
python -u main.py
```

The TUI includes model management, encrypted chat/history support, road-risk scanning, and food/water scanning functionality in the unified `main.py`.

## Model setup

From the TUI, use the model manager to download and verify the configured GGUF model, encrypt it, and remove plaintext when requested. Model integrity checks should be treated separately from the experimental risk-scanning output: a correctly hashed model proves artifact identity, not the truth of a prediction.

## Risk labels

Scanner output is reduced to:

```text
Low | Medium | High
```

Use the result as one input among ordinary evidence. For road use, inspect weather, visibility, traffic, tires, brakes, vehicle condition, obstacles, and route conditions. For food/water use, inspect source, storage, temperature, packaging, recalls/advisories, contamination evidence, and professional test results where appropriate.

# Security model

The installer is designed to fail closed around several important boundaries:

- the required Termux keystore alias must exist on Android installs;
- the liboqs archive must match the pinned SHA-256 before extraction;
- the liboqs-python archive must match its pinned SHA-256 before installation;
- the required OQS KEM mechanisms must be present after compilation;
- normal launch scripts explicitly select SpookyNaza `tri` mode;
- sensitive local key/storage operations use the hardened Naza storage path.

Cryptography cannot make an experimental physical-risk inference scientifically validated. These are separate properties: the cryptographic controls protect software state and artifact integrity; real-world claims still require independent evidence.

## Post-Quantum Supply-Chain Integrity

The original Naza GitHub Actions/PQ supply-chain pipeline is included in this package. `.github/workflows/lock-requirements.yml` regenerates a hash-locked `requirements.txt`, verifies the pinned **liboqs 0.14.0** archive SHA-256 before extraction/build, installs the pinned Python OQS wrapper, creates a canonical lock manifest, signs it with Dilithium2, verifies that signature as a self-check, and publishes the lock artifacts.

Included provenance artifacts from the original Naza repository:

- `.github/workflows/lock-requirements.yml`
- `lock.manifest.json`
- `lock.manifest.pqsig`
- `pq_pubkey.b64`
- `tests/test_ci_security.py`

Pinned liboqs 0.14.0 SHA-256:

```text
5b0df6138763b3fc4e385d58dbb2ee7c7c508a64a413d76a917529e3a9a207ea
```

The historical signed manifest records the SHA-256 of the original generated `requirements.txt` as `0e2bf2b1ab253ea518860fca08b101addad3a2a15c466e4c39d3d29dab92704a`. Running the GitHub Action generates a fresh hash-locked requirements file and a fresh PQ-signed manifest/signature/public-key set for the dependency state at that run.
